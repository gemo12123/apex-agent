# 工程基线与模块骨架详细设计

## 模块设计定位

本分册建立可迁移、可比较、可回滚的工程地基，不改变 Agent 目标行为。它通过 legacy 保持旧链路参与构建，通过 Golden File 固定外部兼容面，通过架构测试把八模块依赖方向变成自动门禁。

## FND-01 冻结现有行为与协议基线

### 实现目标

在任何生产源码迁移前形成可重复的行为样本，区分三类事实：必须保持的外部协议、需迁移保留的内部语义、明确要删除的 PlanExecutor 行为。基线失败时先修复测试环境或登记豁免，不能用目标实现掩盖现状。

### 涉及模块/类

- 当前单模块测试：`ChatControllerTest`、`ChatServiceTest`、`SuperAgentTest`、`SuperAgentFactoryTest`、`SuperAgentSessionServiceTest`、`ToolCallProcessorTest`、`HumanInLoopResumerTest`、`ModelResponseStreamerTest`、`DefaultAgentLifecycleHookRuntimeTest`。
- 当前协议：`message/*`、`constant/AgentEventType`、`domain/dto/ChatRequest`、`util/JacksonUtils`。
- 当前依赖/API：根 POM 的 Spring AI、Spring AI Alibaba、Spring Framework 声明，resolved dependency tree，以及 RUN-02 直接使用的 ChatModel/Message/ChatResponse/ToolCall/ToolResponse/ChatOptions 类。
- 新增测试资源建议放在 `src/test/resources/golden/protocol/` 和 `src/test/resources/golden/scenarios/`。

### 核心流程

1. 记录 JDK、Maven、激活 profile、依赖树和当前 Git 提交。
2. 运行全量测试并从 Surefire XML 统计测试数，而不是从控制台手写数字。
3. 用现有实现驱动六类特征场景，记录出站事件序列、Turn/Iteration、对话和挂起状态。
4. 将协议 JSON 规范化为 UTF-8、LF、无尾随空格的 Golden File；数组顺序保留，对象字段比较采用 JsonNode 结构，END 另做原始字符串精确断言。
5. 建立 `BaselineManifest`，记录样本名、生产者、测试类、目标保留/删除分类和文件 SHA-256。
6. 导出 Spring AI 相关 declared/resolved tree；用类的 `ProtectionDomain.codeSource`/包 implementation version 或等价方式记录实际 jar，并通过编译夹具/反射清单记录 RUN-02 关键构造器和方法签名。

### 接口和数据结构

测试侧新增：

```java
record BaselineCase(
        String id,
        BaselineCategory category,
        String testClass,
        List<String> goldenFiles,
        String expectedDisposition) {}
```

`BaselineCategory` 为 `WIRE_COMPATIBILITY`、`CORE_BEHAVIOR`、`LEGACY_ONLY`。该类型只存在测试源码，不进入产品模块。

依赖证据使用表格而非产品类型：

```text
coordinate | declaredBy | declaredVersion | resolvedVersion | selectedBy | jarSource
apiClass | jarSource | constructors | methodsUsedByCurrentCode
```

原始 dependency tree 与生成命令作为 CI/任务证据保存，摘要进入基线报告；不得只手工抄写最终版本。

### 关键实现逻辑

- SSE 捕获器记录 `SseEmitter.send` 的原始字符串和逻辑顺序，不能只断言反序列化对象。
- 多 ToolCall 样本必须是“第一个成功写入结果、第二个挂起”，用于验证迁移后前序结果不丢失。
- ask_human 样本使用前端真实载荷 `{interaction_type, answers}`；工具确认样本包含 `confirmation_id`、decision 和允许/不允许编辑的参数。
- 现有模式相关测试只归档为 `LEGACY_ONLY`，不进入新链路验收。
- 当前 POM/数据源不一致记录为环境事实，不在本任务修生产配置。
- “实际 jar”以测试/应用类路径真正加载结果为准，不能仅凭 POM 最近声明推断。相同类名出现在多个 jar 或 declared/resolved/loaded 三者不一致时必须单列 R-13 证据。

### 异常处理

- 环境或外部 MCP/Skill 路径导致失败时，测试应替换为本地 Fake，不把机器绝对路径加入豁免。
- 当前协议与消息标准不一致时，保留原始捕获，登记差异并阻塞 PRO-02 目标值选择。
- 已有测试失败必须给出测试名、堆栈和复现命令；禁止笼统记录“环境问题”。
- 关键 Spring AI 类无法加载、来源不唯一或 API 签名无法由当前源码编译验证时，记录具体 coordinate/class/method 并阻塞 RUN-02 候选选择；FND-01 不通过升级依赖消除证据。

### 测试方案

- `mvn -f apex-agent/pom.xml test`。
- 对每个 Golden File做“现有生产者生成 -> 序列化 -> 比较”测试。
- 验证普通 Turn、多 Iteration、多 ToolCall 挂起、ask_human、工具确认、pre-hook 不重复六类场景。
- 断言 `END` 为 `{"event_type":"END"}`、react 事件无 stage_id。
- 运行 verbose dependency tree 与关键 API 编译夹具，检查报告覆盖 Q-17 要求的全部类型和版本来源。

### 架构符合性

该任务冻结既有外部可观察行为，不固化将删除的执行模式，从而给后续模块化重写提供稳定替换门槛，符合“既有聊天/SSE 零破坏”和“唯一 ReAct”双重约束；Q-14 新增状态查询另立增量 Golden File。

## FND-02 建立父 POM、临时 legacy 与八模块骨架

### 实现目标

将根 `apex-agent/pom.xml` 改为聚合 POM时，保证现有源码、资源、测试和 Spring Boot 入口全部进入 `legacy`，避免父 POM 切换造成“构建通过但旧代码没有参与”的假阳性。

### 涉及模块/类

- 移动：`apex-agent/src/main` -> `apex-agent/legacy/src/main`，`src/test` -> `legacy/src/test`。
- 新建：`legacy/pom.xml` 和八个模块的 `pom.xml`、空标准目录。
- 根 POM：properties、dependencyManagement、pluginManagement、modules、Enforcer。
- FND-01 证据：Spring AI declared/resolved tree、BOM/override 来源、实际 jar 与关键 API 签名清单。
- 不改 Java package，不改资源相对路径，不改 `ApexApplication`。

### 核心流程

1. 校验 FND-01 manifest 与基线测试通过。
2. 一次性移动根源码、测试、资源到 legacy，先让 `mvn -pl legacy test` 通过。
3. 根 POM 改为 `packaging=pom`，聚合 legacy 与八模块。
4. 七个代码模块只建立最终依赖边，memory 仅建立无依赖 `packaging=pom` 占位和非标准 archive 目录，暂不复制 legacy 依赖。
5. legacy 保留当前完整依赖和 Boot repackage；父 reactor 执行同一基线。
6. 写入迁移豁免 YAML，所有条目包含规则、原因、责任任务、到期任务。
7. 当前 Spring AI 冲突只允许登记精确 artifact 豁免，owner/到期任务均为 RUN-02；父级 convergence 规则本身保持启用。

### 接口和数据结构

父模块顺序固定：`protocol`、`common`、`core-extension`、`core`、`kit`、`runtime`、`platform`、`memory`、迁移期 `legacy`。顺序只优化 reactor 构建，不替代真实 Maven 依赖。

目标 POM 的直接项目依赖固定为：common→protocol；core-extension→protocol/common；core→protocol/common/core-extension；kit→protocol/common/core-extension；runtime→protocol/common/core-extension/core/kit；platform→protocol/common/core-extension/runtime；memory 无项目依赖且 `packaging=pom`。该表按标准源码直接引用展开，不得为了让 dependency tree 更短而删除冗余边；archive 中旧 import 不参与依赖图。

豁免结构：

```yaml
- rule: legacy-fastjson
  reason: SubAgent 与旧工具处理尚未迁移
  owner: RUN-07
  expires-at-task: CLEAN-02
```

R-13 豁免还必须增加 `coordinates`、`baseline-evidence`，且 `expires-at-task` 固定为 `RUN-02`；禁止用 `org.springframework.ai:*` 整组豁免。

### 关键实现逻辑

- 父 POM 只管理版本；Spring Boot repackage execution 仅在 legacy 子 POM显式启用，不能从父插件配置继承到所有库模块。
- JUnit 4 仅作为 legacy 临时依赖；目标模块统一 JUnit 5。
- FND-02 保留并集中当前依赖声明，不在骨架任务猜测 Spring AI 目标版本。RUN-02 按 Q-17 选择与当前 ChatModel 实际兼容的单一集合；若确需新版本值，只能在 RUN-02 提交中依据已归档失败证据最小调整父 BOM/属性。
- 当前源码事实是 POM 启用 MySQL、application.yml 配 PostgreSQL；不假定有用户未提交 POM 修改。数据库依赖只在 PLAT-03A 迁入 platform。
- 目标模块不得依赖 legacy；可用 Enforcer bannedDependencies 和 `dependency:tree` 检查。

### 异常处理

- 文件移动后资源加载失败，先修 legacy 的资源目录声明，不修改业务资源 URI。
- Boot main class 找不到时，在 legacy 插件中显式指定现有 `org.gemo.apex.ApexApplication`。
- reactor 出现循环或未声明依赖时阻塞提交，不能用 scope/system 或类路径复制绕过。
- Spring AI 精确豁免不能让目标模块构建失败被忽略；它只豁免 convergence 冲突。编译/测试仍必须执行，豁免缺证据或范围过宽时阻塞 FND-02。

### 测试方案

- 移动前后分别运行全量基线并比较 Surefire 报告。
- `mvn -f apex-agent/pom.xml test`。
- `mvn -f apex-agent/pom.xml -pl legacy test`。
- `mvn -f apex-agent/pom.xml -pl legacy spring-boot:repackage -DskipTests` 或等价 package 验证。
- 脚本检查八个目标 POM 无 legacy dependency。
- 保存带 `-Dverbose` 的 Spring AI 相关 dependency tree，并校验每条临时豁免都能回指 FND-01 基线冲突。

### 架构符合性

legacy 是迁移支架而非第九个目标模块；它只允许依赖目标模块，不能成为目标模块的基础。该方向保证新架构逐步接管而不会形成永久环。

## FND-03A 建立架构测试基础设施

### 实现目标

建立一个由父 reactor 自动运行、后续模块可追加规则的架构测试模块或测试套件，先守住“目标模块不依赖 legacy”和“模块无环”两条迁移底线。

### 涉及模块/类

- 建议新增测试承载模块 `architecture-tests` 仅作为迁移期构建辅助；若最终模块必须严格为八个，则在 CLEAN-02 前把测试迁入父构建可执行位置并删除辅助模块。
- 更简方案：将 Maven Enforcer 放父 POM，各模块 ArchUnit 测试放本模块 test 源码；本设计推荐该方案，避免新增目标外 artifact。
- 父 POM：`maven-enforcer-plugin`、`maven-dependency-plugin`。

### 核心流程

1. 父 `validate` 运行依赖收敛、禁止目标模块依赖 legacy、禁止 system scope。
2. 每个模块 `test` 运行本模块包/类型规则。
3. 规则通过共享 test-jar 或复制极小的规则 DSL 接口注册；不共享模块业务类。
4. 迁移豁免由单一 YAML 读取，过期任务达到后自动失败。

### 接口和数据结构

测试侧提供 `ArchitectureRuleDescriptor(ruleId, ownerModule, rationale, expiryTask)`。规则 ID 稳定，失败输出必须带整改任务。

### 关键实现逻辑

- Maven 依赖图用 Enforcer/Dependency Analyzer 检查；对每个目标模块执行 used-declared/used-undeclared 分析，直接引用传递依赖必须失败。Java import 与类型形态用 ArchUnit 检查。
- `legacy -> target` 允许，`target -> legacy` 绝对禁止，不设置包级宽泛豁免。
- 规则测试必须扫描编译产物而非只 grep 源码，以防注解处理或嵌套类型绕过。

### 异常处理

- 架构测试工具在 JDK 25 不兼容时，优先升级测试工具小版本，不改变生产框架版本；仍不兼容则用 `jdeps`/字节码扫描替代并记录原因。
- 读取不到豁免文件应失败关闭，不视为空豁免。

### 测试方案

- 人为给 protocol 加 legacy dependency，验证 validate 失败后回退测试改动。
- 人为形成两个测试模块循环，验证 Enforcer 失败。
- 验证父 `test`/`verify` 自动包含规则，无需单独手工命令。

### 架构符合性

架构守卫把文档约束转化为持续验证，避免模块迁移后再次由便利性引入反向依赖。

## FND-03B 收口最终全模块架构规则

### 实现目标

在 legacy 删除后把目标架构的全部禁止关系、类型边界和技术栈限制纳入标准构建，并清零迁移豁免。

### 涉及模块/类

- 八模块 POM、七个代码模块 ArchUnit 测试、父 Enforcer、依赖树快照和 memory 归档边界检查。
- 重点扫描：protocol DTO、common imports、core-extension 顶级类型、core/runtime 依赖、memory POM/source root、AGENT_BUILD 调用点、Fastjson。

### 核心流程

1. 汇总各模块已落地规则并去重。
2. 删除 legacy 相关允许规则与全部过期豁免。
3. 对 Maven graph、字节码引用、源码关键语义做三层检查。
4. 将反例注入测试作为架构测试自身的测试，证明每条规则能失败。

### 接口和数据结构

最终规则至少包括：

- `protocol` 只能依赖 JDK/Jackson/Lombok（若保留）。
- 七个代码模块直接项目依赖集合与 FND-02 固定表精确一致且 used-but-undeclared 为零；memory 无 dependencies/source root，archive 未进入构建。
- `common` 不引用 `org.springframework`、`jakarta.servlet`、MyBatis/JPA。
- `core-extension` 所有顶级 class file 的 `ACC_INTERFACE` 为真，且无非抽象 default 方法字节码。
- core 不引用 runtime/platform/memory/Spring IoC/Servlet。
- runtime 不引用 platform/memory。
- platform dependency tree 不含 memory。
- 依赖树不含 Fastjson；react 不存在 Mode enum。
- AGENT_BUILD 分发入口只在 core Assembler。

### 关键实现逻辑

- “只含 interface”允许编译器生成的接口内部 synthetic 类型，但禁止用户声明的嵌套实现；扫描需区分 synthetic flag。
- AGENT_BUILD 调用点用 ArchUnit 依赖规则加源码 `rg` 双保险，因为仅靠包依赖无法发现 runtime 复制状态机。
- 最终父 modules 精确等于八个目标模块，不保留 architecture-tests、legacy 或示例聚合模块。

### 异常处理

- 任何过期豁免都视为构建失败，不允许延长到“以后清理”而无新确认。
- 第三方传递依赖含 Fastjson 时，必须 exclusion 或替换适配，不可只检查直接依赖。

### 测试方案

- 父 `mvn test` 和 `mvn verify`。
- `dependency:tree` 保存为交付证据。
- `dependency:analyze` 或等价字节码分析对每个模块执行；fixture 删除 core-extension 的 protocol 直接依赖时必须因 AgentMessage 引用失败。
- 为每类规则建立反例 fixture 或临时 mutation 测试。
- 检查父 modules 和最终目录严格为八模块。

### 架构符合性

最终规则与目标依赖图一一对应，并补充“核心构造语义只在 core”和“memory 不进入默认产品”的行为边界，形成可持续的架构合规闭环。
