# Apex 前端交互规范

## 1. 适用范围

本文基于 `apex-frontend/src` 当前实现整理，覆盖以下前端交互主题：

- SSE 协议事件的接收、归并与状态切换
- 对话区中的各类交互卡片处理方式
- 执行时间线抽屉的投影、展开与导出规则
- Agent 选择、用户标识与会话生命周期

本文是“按当前代码行为归纳出的规范”，后续新增事件类型或新卡片类型时，应同步更新本文。

## 2. 前端交互总览

当前工作台由四个核心层组成：

1. `services/apex-api.ts`
   负责 HTTP 与 SSE 协议接入，包括获取 Agent 列表与发起流式聊天。
2. `stores/session/store.ts`
   负责工作台会话编排，包括初始化、发起对话、处理中断、人机恢复、工具确认恢复与会话重置。
3. `stores/session/reducer.ts`
   负责把后端 SSE 事件归并为前端 `SessionViewModel`。
4. `features/workspace/components/*`
   负责把 `SessionViewModel` 渲染成左侧侧栏、统一主工作区、交互卡片与右侧时间线抽屉。

规范上必须坚持：

- 协议处理与视图渲染分层，组件不直接解析后端原始 SSE 消息。
- 所有流式状态更新统一进入 `applyEnvelope`。
- 所有人机交互恢复都通过 `ChatRequest.type = 'HUMAN_RESPONSE'` 回传。

## 3. 协议处理规范

### 3.1 API 入口

`createApexApiClient` 提供两个入口：

- `fetchAgents(userId)`
  通过 `GET /apex-api/sse/agents` 获取 Agent 列表。
- `streamChat(request, userId, signal, onEnvelope)`
  通过 `POST /apex-api/sse/chat` 发起 SSE 会话。

请求头规范：

- 必带 `Content-Type: application/json`
- 必带 `X-User-Id`

说明：

- `userId` 是前端多会话、多用户隔离的显式上下文，不允许在请求时省略。
- SSE 事件体按 `SseEnvelope` 解析，前端不依赖 `event` 名称，而依赖 `event.data` 中的 JSON 内容。

### 3.2 会话请求类型

当前只允许两种请求类型：

- `NEW`
  新一轮用户问题。
- `HUMAN_RESPONSE`
  人工补充、确认或工具审批后的恢复请求。

规范要求：

- 新问题必须带 `query`。
- 恢复请求允许 `query` 为空，但必须带 `humanResponse`。
- 两类请求都必须带 `sessionId` 与 `agentKey`。

### 3.3 SSE 事件到状态模型的映射

`applyEnvelope` 是唯一合法入口，事件处理规则如下：

- `STREAM_THINK`
  追加到当前 assistant 消息的 `think` 字段，并将会话状态设为 `streaming`。
- `STREAM_CONTENT`
  追加到当前 assistant 消息的 `content` 字段，并按 `context.content_id` 聚合到 `flows`。
- `INVOCATION_DECLARED`
  在指定阶段下创建或覆盖调用记录。
- `INVOCATION_CHANGE`
  支持调用状态变化与内容增量追加。
- `ARTIFACT_DECLARED`
  根据 `scope` 写入全局产物或阶段产物。
- `ARTIFACT_CHANGE`
  只做内容追加，不重建产物对象。
- `HUMAN_INTERVENTION`
  按 `messages` 顺序展开为统一 `pendingInterventions`：ASK_HUMAN 的每个问题各生成一张卡片，TOOL_CONFIRMATION 各生成一张卡片；状态切换为 `waiting-intervention`。
- `TASK_ERROR`
  状态切换为 `error`，展示 `messages[0].message`；消息为空或空白时使用“Agent 执行失败。”。
- `END`
  根据 `context.execution_status` 和当前挂起项推断最终状态。

说明：PLAN 与 TASK_THINK 事件已从协议和前端联合类型删除。STREAM_THINK 与 ARTIFACT 是历史协议兼容能力，当前后端唯一 ReAct 链默认不生产。

### 3.4 END 事件状态收口规则

`END` 事件必须遵守以下收口规则：

- `execution_status = FAILED`
  前端状态进入 `error`。
- `execution_status = HUMAN_IN_THE_LOOP`
  保持 `waiting-intervention`。
- `execution_status = COMPLETED`
  前端状态进入 `completed`。
- 未提供 `execution_status`
  走兼容逻辑：
  - 当前状态已经是 `error` 时保持 `error`
  - 有 `pendingInterventions` 则为 `waiting-intervention`
  - 否则为 `completed`

规范要求：

- 前端不得仅凭流结束就默认完成。
- 人工问题与工具确认统一使用显式 `waiting-intervention` 状态。

现状说明：后端当前发送的 `END` 是不带 `context` 的 `{"event_type":"END"}`。失败链路会先收到 `TASK_ERROR`，因此裸 END 必须保留既有 error 状态；显式 execution_status 分支仍为协议兼容能力并已被测试锁定，不要删除。

### 3.5 模式与上下文处理

`EnvelopeContext.mode` 在当前默认链路固定为 `react`。前端仍把兼容事件中的 mode 保存到 `session.currentMode`，但不据此切换执行引擎或页面结构。

规范要求：

- 任何新增模式，至少要保证现有状态机不崩溃。
- 如果未来需要模式级差异化 UI，应以 `currentMode` 为唯一判断源，不能从文案或阶段名反推。

## 4. 会话与状态管理规范

### 4.1 初始化规则

`initialize()` 行为如下：

- 首次进入页面时加载 Agent 列表
- 加载中禁止重复请求
- 如果当前 `selectedAgentKey` 仍存在于返回列表，保留原选择
- 否则回退到返回列表第一个 Agent
- 拉取失败时：
  - 写入错误消息
  - 回退为单个 `default_agent`

初始化还会读取 `localStorage['apex:active-session:v1']`：

- locator 必须同时匹配当前 `userId`、`agentKey` 和 `sessionId`。
- 调用只读会话状态接口；HUMAN_IN_THE_LOOP 时把批量 HUMAN_INTERVENTION 交给既有 reducer 回显。
- 回显不创建新消息流，也不自动提交 HUMAN_RESPONSE。
- 终态、404、切用户或损坏 locator 清除；5xx 保留并允许下次初始化重试。

### 4.2 用户标识规则

`userId` 来源按以下优先级确定：

1. `localStorage['apex:user-id']`
2. `VITE_APEX_USER_ID`
3. `'demo-user'`

输入规则：

- 前端保存时会 `trim`
- 空值会回退为 `'demo-user'`
- 变更会实时写回 `localStorage`

### 4.3 会话重置规则

`resetSession()` 只重置当前会话态，不重置以下信息：

- `selectedAgentKey`
- `userId`

重置时必须：

- 中止当前流
- 清空错误信息
- 用全新的 `SessionViewModel` 替换会话
- 让主工作区回到欢迎态

这意味着“新建会话”是工作台级重置，不是用户上下文重置。

### 4.4 并发与中止规则

发起 `runChat()` 前，前端会先终止上一个 `AbortController`。

规范要求：

- 任意时刻只能有一个活跃流。
- 用户点击“停止接收”后，状态进入 `aborted`。
- 新请求会覆盖旧流，避免同一会话并发写入状态树。

## 5. 对话区交互规范

### 5.1 消息模型

对话区只渲染两类消息：

- `user`
- `assistant`

其中 assistant 消息包含：

- `content`
- `think`
- `flows`

渲染规则：

- 用户消息按纯文本展示。
- assistant 的 `content` 与 `think` 都用 Markdown 渲染。
- `think` 放在可折叠 `details` 中，默认收起。
- assistant 内容为空时，显示“正在生成回复...”占位。

### 5.2 自动滚动规则

以下任一变化发生时，对话区滚动到底部：

- `messages.length`
- `pendingInterventions.length`
- `status`

规范要求：

- 新消息、等待卡片出现、状态切换都必须对用户可见。
- 自动滚动只作用于对话滚动容器，不影响页面整体滚动位置。

### 5.3 输入框可用状态

主输入框在以下状态禁用：

- `streaming`
- `waiting-intervention`

原因：

- 流式执行过程中不允许叠加新问题
- 人工介入批次未提交前不允许主对话继续

发送规则：

- `Enter` 直接提交
- 空白内容不提交
- 提交后本地草稿立即清空

## 6. 人机交互卡片规范

组件：`HumanPromptCard.vue`

每个问题独立成卡，支持“保存回答”和“跳过”。这两个动作只更新本地 `resolution`，不发起恢复请求；跳过不写入 payload。批次中最后一张卡片显示“提交并继续”，只有全部问题和工具确认均已回答或跳过时才启用。

### 6.1 输入类型

当前支持四种输入类型：

- `TEXT_INPUT`
- `SINGLE_SELECT`
- `CONFIRM`
- `MULTI_SELECT`

卡片头部统一展示：

- 输入类型标签
- 问题标题
- 可选说明文案

### 6.2 CONFIRM 交互

`CONFIRM` 类型不显示文本域，直接显示两个动作按钮：

- 取消
- 确认

当前回传值是纯文本：

- 取消时回传 `'取消'`
- 确认时回传 `'确认'`

规范要求：

- 后端必须接受基于文本语义的确认值。
- 如果未来要改为布尔值，必须同步调整恢复协议和测试。

### 6.3 SINGLE_SELECT 与 TEXT_INPUT 交互

行为规则：

- 若有 `options`，点击选项会写入 `singleValue`
- 一旦点击选项，会清空自定义输入 `customValue`
- 提交时优先取 `customValue.trim()`，其次取选中项

这意味着当前实现允许：

- 先选推荐项，再手动补写为自定义答案
- 用户的自定义文本覆盖预设选项

### 6.4 MULTI_SELECT 交互

行为规则：

- 选项使用可切换的多选 chip
- 提交值由“已勾选项 + 自定义文本”拼接组成
- 自定义文本会作为数组中的一个附加值

规范要求：

- 多选答案必须按数组回传。
- 自定义补充当前只支持一个文本块，不支持结构化多条录入。

### 6.5 多问题与批量恢复规则

同一 `ASK_HUMAN` 项可能包含多个问题。前端按题目顺序展开卡片，提交时只把已回答问题按 `tool_call_id` 重新聚合。

恢复载荷格式：

```json
{
  "tool-call-id": {
    "interaction_type": "ASK_HUMAN",
    "answers": {
      "0": "第一个问题答案",
      "1": ["第二个问题多选答案"]
    }
  }
}
```

规范要求：

- 所有卡片必须进入“已回答”或“已跳过”后才能恢复执行。
- 跳过的问题不出现在 `answers`；某个工具下全部问题都跳过时，该 `tool_call_id` 不出现在 payload。
- 前端以题目顺序 `index` 作为 answers 的 key，后端不得假设是问题文本。
- 整批全部跳过时发送空 `humanResponse: {}`，由 core 在处理每个介入项时即时采用默认值。

## 7. 工具确认卡片规范

组件：`ToolConfirmationCard.vue`

### 7.1 基础结构

卡片由四部分组成：

- 工具展示区：工具名称、标题、描述
- 风险标签：由 `riskLevel` 渲染
- 摘要区：`displayFields`
- 操作区：跳过 / 拒绝 / 确认

如果满足以下条件，才允许编辑参数：

- `confirmation.editable = true`
- `editableFields.length > 0`

### 7.2 默认展示策略

默认先展示摘要，不默认进入编辑态。

这样做的目的：

- 降低高风险操作的认知负担
- 先让用户核对，再决定是否修改参数

### 7.3 编辑态字段类型

当前支持的编辑输入类型：

- `text`
- `textarea`
- `single-select`
- `confirm`
- `date`
- `datetime`

字段映射规则：

- `single-select` 渲染为 `select`
- `textarea` 渲染为 `textarea`
- `date` 渲染为 `input[type=date]`
- `datetime` 渲染为 `input[type=datetime-local]`
- `confirm` 渲染为 checkbox
- 其他默认走 `input[type=text]`

### 7.4 确认按钮可用性

只有在“编辑态 + 必填字段未满足”时，确认按钮才禁用。

必填判定规则：

- 非 `confirm` 字段：`String(value).trim().length > 0`
- `confirm` 字段：必须为 `true`

注意：

- 未进入编辑态时，即使存在必填编辑字段，也允许直接批准并回传空 `updatedArgs`
- 当前实现默认信任“摘要值已足够用于执行”

这是当前代码的真实行为，若业务要求“存在必填可编辑参数时必须先进入编辑态”，需要单独改造。

### 7.5 工具确认回传格式

批准、拒绝或跳过只记录本地结果；与同批问题一起由最后一张卡片统一提交。跳过时不产生该工具的恢复载荷，core 将其解释为默认批准且参数保持原样。

批准时：

```json
{
  "tool-call-id": {
    "interaction_type": "TOOL_CONFIRMATION",
    "confirmation_id": "confirm-id",
    "decision": "APPROVE",
    "updated_args": {
      "field": "value"
    }
  }
}
```

拒绝时：

```json
{
  "tool-call-id": {
    "interaction_type": "TOOL_CONFIRMATION",
    "confirmation_id": "confirm-id",
    "decision": "DENY"
  }
}
```

规范要求：

- `updated_args` 仅在批准且有实际改动时回传。
- `toolCallId` 是恢复执行的主键，`confirmationId` 是同一次工具确认的实例标识，两者都不可省略。
- 显式批准/拒绝必须携带正确的 `confirmationId`；缺失工具键才表示使用默认确认。

## 8. 执行轨迹抽屉规范

### 8.1 时间线投影结构

执行轨迹由 `buildTimelineEntries(session)` 统一投影，组件：`TimelineDrawer.vue` 只消费投影结果，不直接理解 `SessionViewModel` 的内部结构。

时间线节点按以下顺序生成：

1. 逐个阶段展开：阶段节点 → 该阶段的调用节点 → 该阶段的产物节点（按阶段交错，不是先所有阶段再所有调用）
2. 全局产物节点
3. 待人工介入节点（按批次顺序汇总问题和工具确认）
4. 当前会话状态节点（唯一 `defaultExpanded = true` 的节点）

状态文案与视觉语气必须复用 `presentation.ts` 中的 `formatRuntimeStatus`、`formatSessionStatus` 与 `toneFromStatus`，不允许在抽屉组件内重新解释状态。

### 8.2 抽屉开关与默认展开规则

执行轨迹抽屉默认关闭，由中间主工作区（`ChatPane` header）右上角的“执行轨迹”按钮主动打开。注意欢迎态下 `ChatPane` header 整体隐藏，该按钮只在会话开始后可见。抽屉与侧栏的开关状态是 `WorkspacePage.vue` 的本地 `ref`，不在 store 中。

展开规则如下：

- 同一时刻只允许一个节点展开
- 只有 `defaultExpanded = true` 的节点允许首次自动展开
- 若没有默认展开节点，则初次打开时保持全部折叠

桌面端打开抽屉后挤压中间主区宽度，窄屏下退化为覆盖式抽屉。

### 8.3 节点内容与导出

时间线节点详情统一使用 Markdown 渲染。

交互规则如下：

- 点击节点标题切换展开/收起
- `body` 为空时展示“当前节点暂无更多详情”
- 只有带 `exportFileName` 且存在 `body` 的节点才显示“导出”按钮
- 导出使用 `downloadTextFile()`，默认以 UTF-8 文本写出

规范要求：

- 抽屉承担“执行轨迹浏览”和“产物导出”职责
- 抽屉不承担参数编辑、人机恢复或工具审批交互

## 9. Agent 选择规范

### 9.1 选择入口

当前 Agent 选择的唯一入口是左侧侧栏底部“设置”按钮打开的弹层 `TimelineSettingsPopover.vue`（挂在 `WorkspaceSidebar` footer；组件名保留了历史上的 "Timeline" 前缀，但它已不属于时间线抽屉）。弹层内同时承载 `用户 ID` 输入，使用本地草稿 + 显式保存，保存时才写回 store 的 `selectedAgentKey` / `userId`。

`WelcomeScreen` 与 `ChatPane` header 中不再有 Agent 选择控件。

### 9.2 默认值与回退逻辑

初始默认值为：

- `default_agent`

加载远端 Agent 列表后：

- 如果当前值仍存在，保留
- 否则自动切到列表第一项

规范要求：

- 不允许前端根据展示名称判断 Agent 身份，必须使用 `agentKey`。
- 展示文案使用 `agent.name`，请求参数使用 `agent.agentKey`。

### 9.3 会话中的切换语义

会话开始后（`hasStarted` 为真），设置弹层中的 `智能体` 与 `用户 ID` 字段进入禁用态，并提示“对话开始后不可修改智能体和用户 ID”；新建会话后重新可编辑。也就是说 UI 层面已经不允许会话中途切换 Agent。

保留的底层事实：

- 请求始终使用发送瞬间的 `selectedAgentKey`；`session.agentKey` 仍是未写入的保留字段。
- 锁定逻辑在弹层的禁用态，不在 store；通过代码直接调用 `setSelectedAgent` 仍可改值。若业务要求 store 级锁定或服务端拒绝，需要单独实现。

## 10. 页面级交互规范

### 10.1 欢迎态

欢迎态现在属于统一主工作区的一部分，而不是独立页面。

欢迎态承担以下职责：

- 展示产品定位与建议问题
- 提供首轮任务输入框
- 通过建议问题快速回填输入框

`Agent` 选择与 `用户 ID` 输入不再出现在欢迎态中，而是收纳进左侧侧栏底部“设置”按钮打开的弹层（`TimelineSettingsPopover`）。

### 10.2 工作台页

进入工作台后的固定布局为：

- 左侧：默认展开的侧栏，承载“新建会话”、历史对话占位，以及底部“设置”入口（弹层内含 `Agent` 选择与 `用户 ID`）
- 中间：统一主工作区，在欢迎态与已开始会话态之间无缝切换
- 右侧：默认隐藏的执行轨迹抽屉，打开后在桌面端挤压中间区域，窄屏下以覆盖式抽屉出现

布局约束：

- 不再存在“顶部 Header + 右侧上下双面板”的旧结构
- 欢迎态与已开始会话态共用同一个 `ChatPane`
- 右侧抽屉只在用户主动打开时出现

### 10.3 新建会话

“新建会话”按钮位于左侧侧栏顶部，其行为不是路由跳转，而是由 `WorkspacePage` 的 `handleNewChat()` 先关闭侧栏/执行轨迹抽屉（页面本地状态），再调用 `resetSession()`：

- 清空当前会话内容
- 保留 Agent 选择
- 保留用户 ID
- 关闭执行轨迹抽屉（由页面负责，store 不管理抽屉状态）
- 让主工作区回到欢迎态

这是当前用户体验的重要约束，后续若改成“彻底重置”，需要同步更新 store 与页面测试。

## 11. 渲染与安全规范

### 11.1 Markdown 渲染

当前 Markdown 配置为：

- `html: false`
- `linkify: true`
- `breaks: true`

规范要求：

- 前端允许链接自动识别
- 不允许直接渲染原始 HTML
- 多行内容按换行展示

### 11.2 文本下载

产物下载通过浏览器 Blob 完成，MIME 为：

- `text/plain;charset=utf-8`

规范要求：

- 产物导出默认按 UTF-8 文本处理
- 当前未根据 `dataType` 区分 MIME，若未来支持非文本产物，需要扩展下载策略

## 12. 当前实现中的注意事项

### 12.1 文案编码

历史版本中 `apex-api.ts`、`store.ts`、`presentation.ts` 和部分 Vue 组件的中文文案曾出现乱码，目前已全部恢复为正常 UTF-8。新增或修改文案时保持文件为 UTF-8/LF，提交前抽查中文可读性。

另外 `src/features/workspace/components/` 下的 `ExecutionRail.vue` 与 `DetailPanel.vue` 是旧布局的无引用遗留组件（无测试守护），不要把它们当作当前交互的依据。

### 12.2 Agent 与 session 的耦合边界未锁定

当前 `session.agentKey` 在状态模型中存在，但未在发送请求前同步写入，也未作为前端展示判断依据。

这意味着：

- 前端真实生效的 Agent 来源是 `selectedAgentKey`
- `session.agentKey` 当前更像保留字段

后续若要把“会话归属 Agent”展示在 UI 上，应先明确它与 `selectedAgentKey` 的主从关系。

## 13. 后续扩展要求

新增协议或交互时，应至少同步处理以下项目：

1. 在 `types/apex.ts` 中补充协议类型定义
2. 在 `reducer.ts` 中补充状态归并逻辑
3. 在组件层补充对应的展示或交互组件
4. 为新行为补充 store / reducer / 组件测试
5. 更新本文档，保持“代码行为”和“规范描述”一致

如果新增的是人机中断或审批流，必须优先保证：

- 状态机可正确进入等待态
- 恢复载荷可按主键精确回传
- 主输入框在等待期间被禁用
- 用户能在对话区看到明确的待处理卡片
