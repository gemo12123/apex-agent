# 跨端契约参考

修改 REST、SSE、人在回路或任何前后端共享字段时加载本文，并同时读取发生改动一侧的开发参考。完整事件示例见 [消息标准](../spec/消息标准.md)。

## HTTP 边界

| 语义 | 后端 | 前端 |
| --- | --- | --- |
| Agent 列表 | `GET /api/sse/agents` | `fetchAgents()` 请求 `/apex-api/sse/agents` |
| 会话流 | `POST /api/sse/chat`，`text/event-stream` | `streamChat()` 请求 `/apex-api/sse/chat` |
| 用户身份 | `UserContextFilter` 读取 `X-User-Id` | `createHeaders()` 写入 `X-User-Id` |
| 请求模型 | `domain/dto/ChatRequest.java` | `types/apex.ts` 的 `ChatRequest` |
| 新请求 | `type=NEW` | `sendPrompt()` |
| 恢复请求 | `type=HUMAN_RESPONSE` | `answerPrompt()` / `submitConfirmation()` |

Vite 只在本地开发中把 `/apex-api/*` 重写为后端 `/api/*`。不要把前端代理路径误写成后端真实路由。

## SSE 信封

所有事件保持统一外形：

```json
{
  "event_type": "STREAM_CONTENT",
  "context": {},
  "messages": []
}
```

- 后端事件常量：`constant/AgentEventType.java`。
- 后端多态基类：`message/AgentMessage.java`。
- 后端具体载荷：`message/*Message.java`。
- 前端联合类型：`apex-frontend/src/types/apex.ts`。
- 前端消费：`apex-frontend/src/stores/session/reducer.ts`。

JSON 协议使用 snake_case，前端视图模型使用 camelCase。转换应集中在类型构造和 reducer 中，不要让组件直接依赖原始 snake_case 字段。

## 标识符与关联

以下键承担跨事件关联，不能随意生成替代值：

- `sessionId`：一段可恢复会话。
- `agentKey`：Agent 定义和工具装配。
- `content_id`：同一段流式正文的增量聚合。
- `stage_id`：计划阶段；react 模式可能缺失。
- `invocation_id`：调用声明、状态变更和确认卡片。注意主链路当前不发送 `INVOCATION_DECLARED`/`INVOCATION_CHANGE`（仅子 Agent 场景透传），该 ID 实际主要出现在 `TOOL_CONFIRMATION` 中。
- `tool_call_id`：模型工具调用及人类回复的分组键。
- `confirmation_id`：一次工具确认。后端恢复时当前不校验回传的该值，只读取 `decision` 与 `updated_args`。
- `artifact_id`：产物声明与增量更新。两侧类型齐备，但后端当前没有 `ARTIFACT_*` 生产者。

新增事件前先判断是否复用现有标识符。若生产端和消费端无法用同一个稳定键关联，协议尚未设计完整。

## 人在回路

### ASK_HUMAN

- 后端发送问题，并把执行状态切换为 `HUMAN_IN_THE_LOOP`。
- 前端按 `tool_call_id` 收集答案，提交结构为 `{interaction_type: 'ASK_HUMAN', answers: {"<index>": 答案}}`。
- 全部所需答案完成后，以 `HUMAN_RESPONSE` 恢复同一 `sessionId`。
- 已知现状：后端 `HumanInLoopResumer` 恢复时按 `tool_call_id` 取整个提交对象并 `String.valueOf` 注入模型，不解析 `answers`/`interaction_type` 结构。改前端载荷结构时不会被后端反序列化约束，但要保证转字符串后模型可读；改后端解析时要以前端真实提交结构为准（后端旧测试仍断言纯字符串形态）。

### TOOL_CONFIRMATION

- pre-tool Hook（`ToolConfirmHook`）在真实工具执行前发出确认；`editable` 由 `editable_fields` 是否为空派生，`risk_level` 默认 `MEDIUM`。
- 前端回传 `decision=APPROVE|DENY`；批准时可带 `updated_args`。
- 后端只合并 `editable_fields` 中声明过的键，未声明的 `updated_args` 键被忽略；回传的 `confirmation_id` 当前不参与校验。
- 恢复逻辑必须识别已运行的 pre-hook（`executedPreHookBeans` 跳过集），避免重复确认或重复副作用。
- 确认 ID、工具调用 ID、调用 ID 和允许编辑的字段必须互相一致。

任何一类恢复链路的变更都要覆盖“挂起 → END → 用户提交 → 恢复 → 工具/模型继续 → 最终 END”的全过程。

## END 与状态

`END` 表示本轮 SSE 传输结束，不必然表示业务完成。前端 reducer 按 `context.execution_status` 解释（已实现并有测试锁定）：

- `COMPLETED`：会话完成。
- `FAILED`：进入错误态（前端状态值是 `error`）。
- `HUMAN_IN_THE_LOOP`：有待确认工具则 `waiting-confirmation`，否则 `waiting-human`。
- 缺失：按待处理 prompt/confirmation 推断。

已知现状：后端 `SuperAgentCoordinator.sendEnd` 当前发送的是不带 `context` 的 `{"event_type":"END"}`（`ContextKeyEnum.EXECUTION_STATUS` 无任何写入点），因此生产路径永远走“缺失”兜底分支。`ExecutionStatus` 枚举（含 `IN_PROGRESS`）目前只用于服务端会话持久化。后端补发该字段属于兼容增强，前端无需改动；但不要在前端把显式分支当作已被真实流量验证过。

## 新增或修改契约的清单

1. 修改后端常量、消息模型和实际发送点。
2. 为后端序列化、发送或执行状态补测试。
3. 修改前端 detail/envelope 类型与 `SseEnvelope` 联合。
4. 修改 reducer/store，并覆盖增量、缺失字段、等待态和 END。
5. 修改组件与交互测试（如果用户可见）。
6. 更新 [消息标准](../spec/消息标准.md) 的字段、示例和兼容说明。
7. 运行前后端相关测试；公共事件或恢复语义变化时运行两侧完整测试。
