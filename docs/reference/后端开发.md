# 后端开发参考

仅在修改 `apex-agent/` 时加载本文。总体说明见 [项目概览](../overview/项目概览.md)，完整链路见 [架构与执行流程](../overview/架构与执行流程.md)，Hook 类型、生命周期与恢复语义见 [Hook 机制参考](Hook机制.md)。

## 工程与模块

- JDK 25、Maven、Spring Boot 3.4.5。
- 父 reactor 固定包含 `protocol`、`common`、`core-extension`、`core`、`kit`、`runtime`、`platform`、`memory`。
- 前七个模块是代码模块；`memory` 是无依赖的 `packaging=pom` 历史归档占位模块，不编译、不测试、不产出 jar。
- 唯一 Spring Boot 入口是 `platform/.../bootstrap/ApexApplication.java`。
- Spring AI 版本由父 POM 统一管理；关键 `spring-ai-model`、`spring-ai-commons`、`spring-ai-template-st` 解析为 1.1.2。

模块职责和直接项目依赖：

| 模块 | 职责 | 直接项目依赖 |
| --- | --- | --- |
| protocol | HTTP/SSE DTO 与 Golden File | 无 |
| common | 中立领域模型、快照、取消与 JSON | protocol |
| core-extension | 模型、工具、事件、仓储等端口 | protocol、common |
| core | 唯一 ReAct、生命周期、压缩、工具、挂起/恢复 | protocol、common、core-extension |
| kit | ask_human、Skill 激活与资源读取工具、Skill 提示词 Hook、HTTP SubAgent、确认/截断及 Skill 状态 Hook 与组合辅助 | protocol、common、core-extension |
| runtime | Builder、Adapter、lease、Once Publisher、Skill、Spring AI ToolCallback、资源生命周期 | protocol、common、core-extension、core、kit |
| platform | Spring Boot、HTTP/SSE、PostgreSQL/Flyway、Repository | protocol、common、core-extension、runtime |
| memory | 非编译历史归档 | 无 |

## 当前入口

- `GET /api/sse/agents`：`AgentController`。
- `POST /api/sse/chat`：`ChatController -> ChatService -> ApexAgentRuntime -> ApexAgentExecution -> ApexAgent`。
- `GET /api/sse/sessions/{sessionId}?agentKey=...`：只读状态查询；不得获取 lease 或执行模型、Hook、工具。
- `UserContextFilter` 读取 `X-User-Id`，异步执行使用 `UserContextTaskDecorator` 传播并清理上下文。

## 核心执行不变量

- 后端只有一个 ReAct 循环，不存在 PlanExecutor、Stage、执行模式分支或计划工具。
- `Session -> Turn -> Iteration`：一次 Iteration 对应一次模型调用及其工具处理。
- 每个 NEW 或 HUMAN_RESPONSE execution 初始化时只从 Repository 装配一次有效 `ConversationWindow`，随后由请求级 `ApexAgentContext` 持有；同一 execution 的各 Iteration 直接复用该窗口，不重复查询会话历史。
- `ApexAgentContext` 同时持有 Session 级 `SharedDataStore`。AGENT_BUILD、其余 10 个运行期 Hook 与原生 `AgentTool` 在一次 execution 内共享同一实例；HUMAN_RESPONSE 从快照恢复，NEW 继承 Session 中尚未清理的数据。
- 用户、助手和工具消息统一由 Context 写穿：先预计算并校验下一不可变窗口，再提交 `ConversationRepository`，成功后替换内存窗口。Repository 失败时内存窗口不变；恢复重试遇到业务内容相同的稳定 `entryId` 时保留已从数据库加载的消息。
- Hook 的 `AppendMessage`、`ReplaceMessage`、`RemoveMessage` 同样通过 Context 写穿到 ConversationRepository，不存在只修改当前 ModelRequest 的临时普通消息。Replace 保留 entryId、sessionId、turnNo、sortNo、createdTime；Remove 物理删除且不重排 sortNo。
- 11 个生命周期点由 core 分发；只有 `AGENT_BUILD` 能修改定义，且本次分发使用按 `(order, id)` 排序的不可变 Binding 快照。`AppendPrefixDeveloperMessage` 按该顺序追加仅支持 SYSTEM/USER 文本的请求级临时消息；NEW 与 HUMAN_RESPONSE 各重新构建一次，同一请求内的 Iteration 复用构建结果。
- 同一模型响应中的多个 ToolCall 先按顺序完成整批 PRE_TOOL_CALL 预处理，再按顺序消费，保持 ToolCall/ToolResult 一一配对。
- 任一 PRE Hook 请求人工介入时，只停止当前工具的 Hook 分发并继续预处理后续 ToolCall；整批真实工具和 POST_TOOL_CALL 延迟到恢复后执行。
- 批次以 `SuspendedToolBatch` 保存稳定 invocation ID、ToolCall metadata、最终参数、已执行 Hook ID、处置和 typed submission；先保存，再发布唯一 `HUMAN_INTERVENTION`，恢复请求必须使用 `HUMAN_RESPONSE`。
- 恢复只解析当前处理项的稀疏回复，缺失项即时取默认值；已完成的 PRE Hook 不重复执行。再次介入会保存并发布下一批，EndTurn 优先于已收集介入。
- 快照只支持 `1.0.0`；未知版本直接拒绝，不提供升级链。
- 共享数据条目由字符串 key、JSON 值、`ITERATION_END`/`TURN_END`/`NEVER` 清理策略组成。对应结束 Hook 分发完成后才清理；模型最终失败与手动取消会执行 `ITERATION_END`、`TURN_END` 并清理，其他未进入异常收口的 FAILED 路径仍保留短生命周期数据。
- ReAct 循环边界、最后一轮提示和工具强制结束统一使用最终 Agent 定义的 `prompt.maxIterations`；恢复执行与新 Turn 一样从当前模板装配定义并执行 `AGENT_BUILD`，但继续处理原先挂起的 ToolCall 批次。
- `messageCompression` 的消息数、可选 token 阈值和可选字符阈值按 OR 关系触发压缩；容量阈值仅触发压缩，不作为模型调用硬拒绝条件。
- 默认 `ConversationCompactor` 使用当前 execution 的 `ModelGateway` 发起无工具的独立摘要调用，合并已有累计摘要与本次被淘汰消息；它不进入 Agent 主循环，并沿用当前取消令牌。
- `ConversationRepository.load()` 同时返回独立摘要和 `compacted=FALSE` 的未压缩消息；该返回值是有效原始消息的唯一权威。窗口只负责插入独立 `SUMMARY` 并排序，若仓储返回摘要覆盖范围内的未压缩消息则直接拒绝，禁止把摘要拼入 system prompt 或写入普通消息表。
- 压缩提交只标记摘要覆盖范围并更新累计摘要，不重新插入保留尾部。Repository 成功后，Context 的有效窗口同步替换为新累计 `SUMMARY` 与保留尾部；后续 Iteration 直接读取该压缩后窗口。
- ConversationRepository 对外只提供 `load()` 与原子 `commit(ConversationWriteBatch)`；批次有序支持 append、replace、remove、compact。内存实现先在副本预演，PostgreSQL 使用单事务提交。POST_MESSAGE_COMPRESSION 的摘要、压缩标记与消息操作位于同一批次，任一失败共同回滚。
- 主模型消息顺序固定为根 system prompt、`prefixDeveloperMessages`、摘要及对话消息。`ModelRequest.messages` 在调用前必须与当前持久化 ConversationWindow 完全一致，tools 必须来自当前 enabledTools。前置消息计入 token/字符估算但不计入消息数阈值，也不进入压缩源、摘要或保留集合；它是普通消息持久化规则的唯一请求级例外。没有可压缩对话时不执行空压缩。Core 不锁定或校验 Hook 编辑后的工具消息组，相关协议完整性由 Hook 自己保证。
- 主模型调用首次失败后最多重试 3 次，每次失败记录 warning；全部失败后把简短错误写入 Session 运行时快照，先执行 `ITERATION_END`、`TURN_END`，再发布只含异常 message 的 `TASK_ERROR` 和唯一 `{"event_type":"END"}`。普通 Hook 异常只记录 warning 和结构化快照，不中断后续 Hook；普通工具异常转为失败 ToolResult 后继续循环。

## runtime 与取消

- `ApexAgentRuntime` 可脱离 Spring IoC 构建和运行；Builder 必须且只能配置一个 `ModelGateway` 或 `ChatModel`。
- Builder 可注册独立 `ToolCallback` 或 `ToolCallbackProvider`。provider 只在 `build()` 时读取一次；存在 callback 时必须配置唯一 `ToolCallingManager`，`returnDirect=true` 会快速失败。
- NEW/HUMAN_RESPONSE 在返回 execution 前同步争用同一 `sessionId` lease；该协调器只保证单进程安全。
- 每次请求有独立 Publisher、CancellationToken 和活动登记。
- `cancel()`/runtime `close()` 对 RUNNING execution 只发取消命令并返回；core 感知取消后把状态置为 CANCELLED，只执行可用的 `ITERATION_END` 与 `TURN_END` 并绕过取消检查保存终态。模型、Spring AI callback 与 kit 的 HTTP SubAgent Adapter 主动取消底层调用。callback 执行期间通过中断当前执行线程传播取消，退出后清理本次取消产生的中断标记。
- lease 和活动登记仅在实际 `run()` 的 `finally` 中释放；runtime 自有资源在最后一个活动 execution 注销后逆序关闭。
- 不设置取消超时或 grace period。不合作的自定义工具可能长期占用资源，这是公开限制。

## platform 与持久化

- 配置文件：`platform/src/main/resources/application.yml`。
- 默认数据库是 PostgreSQL：`APEX_DB_URL`、`APEX_DB_USER`、`APEX_DB_PASSWORD`。
- Flyway 建立 `apex_agent_session`、`apex_agent_dialogue_message`、`apex_agent_dialogue_summary` 三张表。
- 快照、集合、payload 和长内容均用 `TEXT`，不使用 JSONB；消息以 `(session_id, sort_no)` 唯一约束排序。
- `runtime_snapshot` 保存 Turn/Iteration 元数据、Session 共享数据、结构化 `executionErrors` 和人工介入所需的 `SuspendedToolBatch`，不持久化完整 `modelRequest/modelResponse`。Hook 错误只保存 Turn/Iteration、HookPoint、Binding ID 和简短提示，不保存堆栈；模型最终失败保存最终异常 message。共享值写入时归一化为 JSON 标量、对象或数组，旧快照缺少 `sharedData` 或 `executionErrors` 时按空集合加载。请求级 `prefixDeveloperMessages` 在写入 Iteration 快照前即被剥离，内存仓储同样不会保存。加载时仅为 `ITERATION_END` Hook 根据批次合成包含最终 ToolCall 的最小 `modelResponse`，其 `modelRequest` 为 `null`。旧 `suspended_tool_call` 列只保留历史批次的读取兼容，新写入固定为 `NULL`。
- summary 与 message 提供重新装配后的模型上下文，不承担 ToolCall 控制状态；恢复定义来自当前模板，持久化的定义快照不再作为恢复构造来源。
- `apex_agent_dialogue_message` 只负责对话历史、模型上下文和压缩，不参与恢复执行现场；终态和普通 `IN_PROGRESS` 快照不保留请求、响应或已完成 ToolResult 正文。
- core 编排跨 Repository 提交顺序；Context 与 Conversation Repository 通过写穿顺序保持 execution 内一致，但不提供 Conversation/Session 两个 Repository 之间的原子事务或自动补偿。
- 本期必须单实例部署。共享 PostgreSQL 不能替代分布式 lease。

## 工具、Skill、MCP 与 SubAgent

- 内置交互能力由 kit 提供；固定拒绝、取消和强制结束 ToolResult 只由 core 的 `ToolResultFactory` 生成。
- 普通文件 Skill 的 `FileSkillProvider` 与底层资源加载仍在 runtime；多 Provider 注册表 `RuntimeSkillRegistry` 位于 platform。注册表构建时调用各 `SkillProvider.loadSkills()` 缓存 `SkillMeta` 与 Provider 路由；`FileSkillProvider` 同时创建缓存的 `SkillDefinition`，扫描全部子资源并写入仅含相对路径、含扩展名文件名和 MIME 类型的 `SkillResource` 元信息，此阶段不读取 instructions 或资源 content。首次 `loadSkill(skillName)` 读取并缓存 `SKILL.md` 正文，首次 `loadResource(skillName, resourcePath)` 或 `loadResource("skillName/resourcePath")` 读取并缓存对应 `SkillResource.content`，后续调用不再访问底层文件。多个 Provider 同名时后注册者覆盖先注册者，单个 Provider 内重名直接拒绝。
- standalone runtime 默认使用空 Provider，不隐式扫描文件；Builder 只提供 `skillProvider(...)` 接收单个最终 Provider，多 Provider 场景由调用方自行聚合。platform 在没有原始 `SkillProvider` Bean 时使用 `apex.platform.skills.path` 创建默认 `FileSkillProvider`；存在 Bean 时忽略该路径，并按 Spring 顺序交给 platform 的 `RuntimeSkillRegistry` 聚合。最终 Registry 以 `@Primary SkillProvider` Bean 同时注入 runtime、工具与 Hook；普通消费者应使用单值构造器注入，原始 Provider 不应标记为 `@Primary` 或反向依赖最终 Registry。当前启用/激活 Skill、取消令牌与共享数据仍从工具或 Hook 的执行 Context 获取，`AgentPorts` 不是扩展注入接口。`ActivateSkillTool`、`ReadSkillResourceTool` 和可选 `SkillActivationStateHook` 位于 kit；前两个工具须显式声明，Hook 须显式注册和绑定。core 不识别保留工具名，只校验并持久化 POST_TOOL_CALL Hook 声明的 `SkillActivationDelta`。Skill Learning 已归档，不是默认能力。
- kit 的 `AvailableSkillsPromptHook` 由 platform 使用同一个最终 `RuntimeSkillRegistry` 注册；Agent 显式绑定后，它在 AGENT_BUILD 中按 `enabledSkills` 过滤元信息，并将系统提示词的 `{skills}` 替换为转义后的 `<available_skills>` XML。默认 Agent 未绑定该 Hook。
- `SpringAiToolCallbackAgentTool` 把 callback 定义映射为 `AgentTool`；PRE Hook 批准后，每次只重建一个 ToolCall 交给 `ToolCallingManager`，结果映射回 Apex 后再进入 POST Hook 与持久化。core 始终是唯一 ReAct 和生命周期编排者。
- 原生 `AgentTool` 通过 `ToolExecutionContext.sharedData()` 访问 Session 共享数据；`attributes` 仍只保存 invocation 级不可变元数据。Store 依赖 Session lease 串行使用，不支持扩展保留引用后异步修改。
- kit 提供可选的 `WriteTodosTool` 与 `TodoMiddleware`：`write_todos` 整体替换当前 Turn 的结构化 Todo 列表，列表使用 `TURN_END` 策略保存在共享数据中；PRE_MODEL_CALL 中间件维护一条带稳定 payload 标记的持久化 SYSTEM/TEXT 上下文，首次 Append、状态变化 Replace、重复标记 Remove，Todo 为空时替换为静态规则，压缩淘汰后从共享数据重新 Append。platform 默认注册两者，但 Agent 必须显式声明工具并绑定 Hook 才会启用。
- kit 的 `ToolResultTruncateHook` 将超预算完整正文写入 `{outputDir}/{sessionId}/{filename}`，信封只暴露 filename，并把实际根目录和内容类型登记到 Session 共享数据。可选 `InspectToolResultTool` 通过 `inspect_tool_result` 在同一 Session 内提供 inspect、structure、slice、search 和 JSONPath 定向读取；高级 Jayway JSONPath 不主动拦截，单次结果最多 20000 个序列化字符。platform 注册该工具但默认 Agent 不启用。
- platform 通过 Spring AI MCP Client Starter 收集唯一 Manager、独立 callback 和所有 callback provider。工具发现不等于授权：callback 的最终名称仍必须进入 Agent 的 `available`，并在 session `enabledTools` 中启用后才会暴露或执行。
- kit 的 HTTP SubAgent 使用既有 chat/SSE 协议和独立子 session；远端 HUMAN_INTERVENTION 不透传，子请求被取消并转为父工具普通失败。
- 外部 MCP、Skill 路径和模型密钥不是仓库内置资源，测试应使用 Fake 或临时目录。
