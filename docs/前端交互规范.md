# Apex 前端交互规范

## 1. 适用范围

本文基于 `apex-frontend/src` 当前实现整理，覆盖以下前端交互主题：

- SSE 协议事件的接收、归并与状态切换
- 对话区中的各类交互卡片处理方式
- 执行轨与详情面板的联动规则
- Agent 选择、用户标识与会话生命周期

本文是“按当前代码行为归纳出的规范”，后续新增事件类型或新卡片类型时，应同步更新本文。

## 2. 前端交互总览

当前工作台由四个核心层组成：

1. `services/apex-api.ts`
   负责 HTTP 与 SSE 协议接入，包括获取 Agent 列表与发起流式聊天。
2. `stores/session/store.ts`
   负责工作台会话编排，包括初始化、发起对话、处理中断、人机恢复、工具确认恢复与侧栏选择。
3. `stores/session/reducer.ts`
   负责把后端 SSE 事件归并为前端 `SessionViewModel`。
4. `features/workspace/components/*`
   负责把 `SessionViewModel` 渲染成欢迎页、对话区、交互卡片、执行轨和详情面板。

规范上必须坚持：

- 协议处理与视图渲染分层，组件不直接解析后端原始 SSE 消息。
- 所有流式状态更新统一进入 `applyEnvelope`。
- 所有人机交互恢复都通过 `ChatRequest.type = 'HUMAN_RESPONSE'` 回传。

## 3. 协议处理规范

### 3.1 API 入口

`createApexApiClient` 提供两个入口：

- `fetchAgents(userId)`
  通过 `GET /apex-api/sse/agents` 获取 Agent 列表。
- `streamChat(request, userId, signal, onEnvelope)`
  通过 `POST /apex-api/sse/chat` 发起 SSE 会话。

请求头规范：

- 必带 `Content-Type: application/json`
- 必带 `X-User-Id`

说明：

- `userId` 是前端多会话、多用户隔离的显式上下文，不允许在请求时省略。
- SSE 事件体按 `SseEnvelope` 解析，前端不依赖 `event` 名称，而依赖 `event.data` 中的 JSON 内容。

### 3.2 会话请求类型

当前只允许两种请求类型：

- `NEW`
  新一轮用户问题。
- `HUMAN_RESPONSE`
  人工补充、确认或工具审批后的恢复请求。

规范要求：

- 新问题必须带 `query`。
- 恢复请求允许 `query` 为空，但必须带 `humanResponse`。
- 两类请求都必须带 `sessionId` 与 `agentKey`。

### 3.3 SSE 事件到状态模型的映射

`applyEnvelope` 是唯一合法入口，事件处理规则如下：

- `STREAM_THINK`
  追加到当前 assistant 消息的 `think` 字段，并将会话状态设为 `streaming`。
- `STREAM_CONTENT`
  追加到当前 assistant 消息的 `content` 字段，并按 `context.content_id` 聚合到 `flows`。
- `PLAN_DECLARED`
  用服务端返回的阶段列表重建 `stages`，保留已有阶段下的 `invocations` 与 `artifacts`。
- `PLAN_CHANGE`
  支持阶段状态更新、插入阶段、删除阶段、更新阶段元信息。
- `INVOCATION_DECLARED`
  在指定阶段下创建或覆盖调用记录。
- `INVOCATION_CHANGE`
  支持调用状态变化与内容增量追加。
- `ARTIFACT_DECLARED`
  根据 `scope` 写入全局产物或阶段产物。
- `ARTIFACT_CHANGE`
  只做内容追加，不重建产物对象。
- `ASK_HUMAN`
  生成等待回答的人机卡片，状态切换为 `waiting-human`，并清空待确认工具卡片。
- `TOOL_CONFIRMATION`
  生成工具确认卡片，状态切换为 `waiting-confirmation`，并清空待回答的人机卡片。
- `END`
  根据 `context.execution_status` 和当前挂起项推断最终状态。

### 3.4 END 事件状态收口规则

`END` 事件必须遵守以下收口规则：

- `execution_status = FAILED`
  前端状态进入 `error`。
- `execution_status = HUMAN_IN_THE_LOOP`
  如果有待确认工具，则保持 `waiting-confirmation`；否则保持 `waiting-human`。
- `execution_status = COMPLETED`
  前端状态进入 `completed`。
- 未提供 `execution_status`
  走兼容逻辑：
  - 有待确认工具则为 `waiting-confirmation`
  - 有未答完的人机问题则为 `waiting-human`
  - 否则为 `completed`

规范要求：

- 前端不得仅凭流结束就默认完成。
- 等待人工输入与等待工具确认必须是显式状态。

### 3.5 模式与上下文处理

`EnvelopeContext.mode` 当前主要有：

- `react`
- `plan-executor`

现有前端对模式的处理方式：

- 把 `mode` 保存到 `session.currentMode`
- 不为不同模式渲染不同页面结构
- 通过不同事件组合体现差异：
  - `react` 更常见为直接内容流与实时调用
  - `plan-executor` 更常见为先声明阶段，再逐阶段追加调用和产物

规范要求：

- 任何新增模式，至少要保证现有状态机不崩溃。
- 如果未来需要模式级差异化 UI，应以 `currentMode` 为唯一判断源，不能从文案或阶段名反推。

## 4. 会话与状态管理规范

### 4.1 初始化规则

`initialize()` 行为如下：

- 首次进入页面时加载 Agent 列表
- 加载中禁止重复请求
- 如果当前 `selectedAgentKey` 仍存在于返回列表，保留原选择
- 否则回退到返回列表第一个 Agent
- 拉取失败时：
  - 写入错误消息
  - 回退为单个 `default_agent`

### 4.2 用户标识规则

`userId` 来源按以下优先级确定：

1. `localStorage['apex:user-id']`
2. `VITE_APEX_USER_ID`
3. `'demo-user'`

输入规则：

- 前端保存时会 `trim`
- 空值会回退为 `'demo-user'`
- 变更会实时写回 `localStorage`

### 4.3 会话重置规则

`resetSession()` 只重置当前会话态，不重置以下信息：

- `selectedAgentKey`
- `userId`

重置时必须：

- 中止当前流
- 清空右侧详情选择
- 清空错误信息
- 用全新的 `SessionViewModel` 替换会话

这意味着“返回首页”是工作台级重置，不是用户上下文重置。

### 4.4 并发与中止规则

发起 `runChat()` 前，前端会先终止上一个 `AbortController`。

规范要求：

- 任意时刻只能有一个活跃流。
- 用户点击“停止接收”后，状态进入 `aborted`。
- 新请求会覆盖旧流，避免同一会话并发写入状态树。

## 5. 对话区交互规范

### 5.1 消息模型

对话区只渲染两类消息：

- `user`
- `assistant`

其中 assistant 消息包含：

- `content`
- `think`
- `flows`

渲染规则：

- 用户消息按纯文本展示。
- assistant 的 `content` 与 `think` 都用 Markdown 渲染。
- `think` 放在可折叠 `details` 中，默认收起。
- assistant 内容为空时，显示“正在生成回复...”占位。

### 5.2 自动滚动规则

以下任一变化发生时，对话区滚动到底部：

- `messages.length`
- `pendingPrompts.length`
- `pendingConfirmations.length`
- `status`

规范要求：

- 新消息、等待卡片出现、状态切换都必须对用户可见。
- 自动滚动只作用于对话滚动容器，不影响页面整体滚动位置。

### 5.3 输入框可用状态

主输入框在以下状态禁用：

- `streaming`
- `waiting-human`
- `waiting-confirmation`

原因：

- 流式执行过程中不允许叠加新问题
- 人机问题未完成前不允许主对话继续
- 工具确认未处理前不允许主对话继续

发送规则：

- `Enter` 直接提交
- 空白内容不提交
- 提交后本地草稿立即清空

## 6. 人机交互卡片规范

组件：`HumanPromptCard.vue`

### 6.1 输入类型

当前支持四种输入类型：

- `TEXT_INPUT`
- `SINGLE_SELECT`
- `CONFIRM`
- `MULTI_SELECT`

卡片头部统一展示：

- 输入类型标签
- 问题标题
- 可选说明文案

### 6.2 CONFIRM 交互

`CONFIRM` 类型不显示文本域，直接显示两个动作按钮：

- 取消
- 确认

当前回传值是纯文本：

- 取消时回传 `'取消'`
- 确认时回传 `'确认'`

规范要求：

- 后端必须接受基于文本语义的确认值。
- 如果未来要改为布尔值，必须同步调整恢复协议和测试。

### 6.3 SINGLE_SELECT 与 TEXT_INPUT 交互

行为规则：

- 若有 `options`，点击选项会写入 `singleValue`
- 一旦点击选项，会清空自定义输入 `customValue`
- 提交时优先取 `customValue.trim()`，其次取选中项

这意味着当前实现允许：

- 先选推荐项，再手动补写为自定义答案
- 用户的自定义文本覆盖预设选项

### 6.4 MULTI_SELECT 交互

行为规则：

- 选项使用可切换的多选 chip
- 提交值由“已勾选项 + 自定义文本”拼接组成
- 自定义文本会作为数组中的一个附加值

规范要求：

- 多选答案必须按数组回传。
- 自定义补充当前只支持一个文本块，不支持结构化多条录入。

### 6.5 多问题分组恢复规则

`ASK_HUMAN` 可能一次下发多个问题，但它们会按 `tool_call_id` 聚合恢复。

恢复载荷格式：

```json
{
  "tool-call-id": {
    "interaction_type": "ASK_HUMAN",
    "answers": {
      "0": "第一个问题答案",
      "1": ["第二个问题多选答案"]
    }
  }
}
```

规范要求：

- 同一 `tool_call_id` 下的问题必须全部答完后才能恢复执行。
- 前端以题目顺序 `index` 作为 answers 的 key，后端不得假设是问题文本。

## 7. 工具确认卡片规范

组件：`ToolConfirmationCard.vue`

### 7.1 基础结构

卡片由四部分组成：

- 工具展示区：工具名称、标题、描述
- 风险标签：由 `riskLevel` 渲染
- 摘要区：`displayFields`
- 操作区：拒绝 / 确认

如果满足以下条件，才允许编辑参数：

- `confirmation.editable = true`
- `editableFields.length > 0`

### 7.2 默认展示策略

默认先展示摘要，不默认进入编辑态。

这样做的目的：

- 降低高风险操作的认知负担
- 先让用户核对，再决定是否修改参数

### 7.3 编辑态字段类型

当前支持的编辑输入类型：

- `text`
- `textarea`
- `single-select`
- `confirm`
- `date`
- `datetime`

字段映射规则：

- `single-select` 渲染为 `select`
- `textarea` 渲染为 `textarea`
- `date` 渲染为 `input[type=date]`
- `datetime` 渲染为 `input[type=datetime-local]`
- `confirm` 渲染为 checkbox
- 其他默认走 `input[type=text]`

### 7.4 确认按钮可用性

只有在“编辑态 + 必填字段未满足”时，确认按钮才禁用。

必填判定规则：

- 非 `confirm` 字段：`String(value).trim().length > 0`
- `confirm` 字段：必须为 `true`

注意：

- 未进入编辑态时，即使存在必填编辑字段，也允许直接批准并回传空 `updatedArgs`
- 当前实现默认信任“摘要值已足够用于执行”

这是当前代码的真实行为，若业务要求“存在必填可编辑参数时必须先进入编辑态”，需要单独改造。

### 7.5 工具确认回传格式

批准时：

```json
{
  "tool-call-id": {
    "interaction_type": "TOOL_CONFIRMATION",
    "confirmation_id": "confirm-id",
    "decision": "APPROVE",
    "updated_args": {
      "field": "value"
    }
  }
}
```

拒绝时：

```json
{
  "tool-call-id": {
    "interaction_type": "TOOL_CONFIRMATION",
    "confirmation_id": "confirm-id",
    "decision": "DENY"
  }
}
```

规范要求：

- `updated_args` 仅在批准且有实际改动时回传。
- `toolCallId` 是恢复执行的主键，`confirmationId` 是同一次工具确认的实例标识，两者都不可省略。

## 8. 执行轨与详情联动规范

### 8.1 执行轨结构

组件：`ExecutionRail.vue`

执行轨按以下顺序展示：

1. 全局产物
2. 各阶段卡片
3. 每个阶段下的调用列表
4. 每个阶段下的产物列表

阶段卡片状态由 `toneFromStatus` 与 `formatRuntimeStatus` 统一映射，不允许组件内部各自解释状态文案。

### 8.2 阶段兜底规则

当调用或阶段产物事件没有显式 `stage_id` 时，`reducer` 会创建默认阶段：

- `id = 'react-stage'`

规范含义：

- 即便后端未声明完整计划，前端仍要能承接 ReAct 模式下的实时调用流。
- 新的事件生产方若缺少 `stage_id`，默认会落到实时执行阶段。

### 8.3 详情面板联动

组件：`DetailPanel.vue`

联动规则：

- 点击调用，详情面板展示调用内容
- 点击产物，详情面板展示产物内容
- 同时存在选中的调用和产物时，产物优先展示

展示规则：

- 详情内容统一用 Markdown 渲染
- 调用内容为空时，显示“正在等待调用结果...”
- 产物支持导出为本地 `.md` 文件

规范要求：

- 详情面板是只读查看器，不承担编辑职责。
- 导出使用产物名作为文件名，默认导出为 Markdown 文本。

## 9. Agent 选择规范

### 9.1 选择入口

当前有两个 Agent 选择入口：

- 欢迎页 `WelcomeScreen`
- 已进入会话后的工作台头部 `WorkspacePage`

这两个入口都直接绑定同一个 store 字段：

- `selectedAgentKey`

因此它们必须保持一致的选项源和相同行为。

### 9.2 默认值与回退逻辑

初始默认值为：

- `default_agent`

加载远端 Agent 列表后：

- 如果当前值仍存在，保留
- 否则自动切到列表第一项

规范要求：

- 不允许前端根据展示名称判断 Agent 身份，必须使用 `agentKey`。
- 展示文案使用 `agent.name`，请求参数使用 `agent.agentKey`。

### 9.3 会话中的切换语义

当前实现允许用户在工作台头部切换 Agent，但切换只影响“下一次发送或恢复请求”。

这意味着：

- 已开始的消息流不会因为切换下拉框而重绑定 Agent
- 人机恢复与工具确认恢复会使用提交瞬间的 `selectedAgentKey`

规范建议：

- 如果业务要求“同一 sessionId 内 Agent 不得变更”，应在 store 层增加锁定逻辑。
- 在当前实现下，后端必须能容忍同一会话恢复时携带不同的 `agentKey`，或在服务端显式拒绝。

## 10. 页面级交互规范

### 10.1 欢迎页

欢迎页承担以下职责：

- 展示产品定位与建议问题
- 选择 Agent
- 输入用户 ID
- 发起首轮任务

建议问题点击后只回填输入框，不直接发送。

### 10.2 工作台页

进入工作台后的固定布局为：

- 左侧：对话区
- 右侧上半：执行轨
- 右侧下半：详情面板

移动端或窄屏下转为单列布局，但信息层级不变。

### 10.3 返回首页

“返回首页”按钮行为不是路由跳转，而是：

- 清空当前会话内容
- 保留 Agent 选择
- 保留用户 ID
- 回到欢迎页视图

这是当前用户体验的重要约束，后续若改成“彻底重置”，需要同步更新 store 测试。

## 11. 渲染与安全规范

### 11.1 Markdown 渲染

当前 Markdown 配置为：

- `html: false`
- `linkify: true`
- `breaks: true`

规范要求：

- 前端允许链接自动识别
- 不允许直接渲染原始 HTML
- 多行内容按换行展示

### 11.2 文本下载

产物下载通过浏览器 Blob 完成，MIME 为：

- `text/plain;charset=utf-8`

规范要求：

- 产物导出默认按 UTF-8 文本处理
- 当前未根据 `dataType` 区分 MIME，若未来支持非文本产物，需要扩展下载策略

## 12. 当前实现中的注意事项

### 12.1 文案编码异常

当前部分源码中的中文文案已经出现乱码，主要体现在：

- `apex-api.ts`
- `store.ts`
- `presentation.ts`
- 多个 Vue 组件模板中的中文静态文本

虽然这不改变交互机制，但会直接影响界面文案质量。建议单独做一次编码清理，统一恢复为 UTF-8 正常文案。

### 12.2 Agent 与 session 的耦合边界未锁定

当前 `session.agentKey` 在状态模型中存在，但未在发送请求前同步写入，也未作为前端展示判断依据。

这意味着：

- 前端真实生效的 Agent 来源是 `selectedAgentKey`
- `session.agentKey` 当前更像保留字段

后续若要把“会话归属 Agent”展示在 UI 上，应先明确它与 `selectedAgentKey` 的主从关系。

## 13. 后续扩展要求

新增协议或交互时，应至少同步处理以下项目：

1. 在 `types/apex.ts` 中补充协议类型定义
2. 在 `reducer.ts` 中补充状态归并逻辑
3. 在组件层补充对应的展示或交互组件
4. 为新行为补充 store / reducer / 组件测试
5. 更新本文档，保持“代码行为”和“规范描述”一致

如果新增的是人机中断或审批流，必须优先保证：

- 状态机可正确进入等待态
- 恢复载荷可按主键精确回传
- 主输入框在等待期间被禁用
- 用户能在对话区看到明确的待处理卡片
